# release-notes.md: механизм, покрытие, инструкция автору новостей

Каждый версионный GitHub Release несёт asset `release-notes.md`; тело релиза — тот же файл. Рядом, если текст
сгенерирован, лежит asset `announcement.json` для Discord-бота. Прозу пишет CI, а не агент: action
`Blockfield/blockfield-workspace/.github/actions/release-text` собирает факты и вызывает модель: один запрос пишет
`release-notes.md`, у клиентского выпуска второй запрос пишет анонс. Формат
`release-notes.md`: YAML-заголовок (`schema_version`, `repository`, `version`, `previous_version`, `date`, `kind`,
`backfilled`) и семь разделов. Проверка (`check`) и сверка пинов живут в том же action
(`release_notes_tool.py`, единственная рабочая копия). Файл `scripts/release-notes-tool.py` этого репозитория
оставлен только для ручных издателей форков и ресурсов; файлы `release-notes/<тег>.md` — история уже выпущенных релизов,
новые не создаются.

## Как выпускать

1. Релизный PR готовит только код и пины. Описание можно не писать: если тело PR пусто, workflow `pr-text.yml` при
   открытии заполняет его по diff и коммитам (что изменилось, как проверено, строка «Для игроков: …»). Если автор
   написал описание без строки «Для игроков: …», она дописывается по diff: из неё анонс узнаёт, что заметит игрок.
   Нужно лишь осмысленное название PR.
2. Тег. Job публикации вызывает action (`mode: release`) **до** создания релиза и прикладывает `release-notes.md` и
   `announcement.json` в момент создания, чтобы бот увидел оба файла на событии `published`. Action:
   - берёт `previous_version` — последний опубликованный (не draft) релиз той же линии ниже тега; сожжённые номера
     релиза не имеют и пропускаются сами;
   - сверяет пины: обновление, откат, добавление, удаление, смену адреса при тех же байтах — и подтягивает «Кратко» и
     «Для игроков» из release-notes.md компонента за **все** версии промежутка;
   - собирает слитые PR промежутка (merge-коммиты `previous..тег`) с названиями, описаниями и заголовками коммитов, а у
     каждого компонента — его слитые PR между старым и новым тегом пина (без ботов и подписей Blacksmith); выдержки
     release-notes компонента идут рядом, «не восстановлено» отбрасывается;
   - у клиента сверяет отпечаток `client` из build.json с предыдущим релизом: совпадение даёт «в клиентской сборке
     изменений нет — подтверждено отпечатком»;
   - запросом к OpenRouter (`OPENROUTER_API_KEY`, модель из `RELEASE_TEXT_MODEL`) получает `release-notes.md` и
     проверяет его: `check`, схема JSON, чёрный список (чужие хосты, IP, Dokploy, webhook, homeserver, ghcr), присутствие
     каждого изменённого компонента, а в «Кратко» и «Для игроков» — отсутствие заглушек («обновлён X с vA до vB»,
     «подробности не восстановлены», «Рекомендуется обновиться»): игроку пишут, ЧТО изменилось, а номера версий
     остаются в «Технические изменения» и «Обновлённые компоненты». Нет никаких сведений — «Для игроков» прямо
     говорит, что видимых изменений установить не удалось. При отказе проверки — одна повторная попытка с текстом
     ошибок;
   - у клиента отдельным запросом (модель из `ANNOUNCEMENT_MODEL`, иначе `RELEASE_TEXT_MODEL`) пишет анонс по тем же
     фактам: промпт `prompts/announcement.md` с образцами и общий словарь `prompts/glossary.md` (идентификаторы из кода
     → слова игрока). Проверка отклоняет заглушки, утечки, пустые списки при наличии изменений; идентификаторы из кода,
     служебные слова, обращение «Сообщество…» и списки не через «• » отправляют на повтор, а на третьей попытке
     остаются предупреждением. Изменения редактора карт и Workshop идут в `creators`, действие игрока — в
     `compatibility`.
3. Резервный путь. Нет ключа или модели, сбой API, не прошла проверка: `release-notes.md` собирается только из фактов
   (названия PR, пины, выдержки компонентов, в «Источниках» строки «Неполнота: …») и проходит тот же `check`;
   `announcement.json` не создаётся, бот разбирает `release-notes.md` сам. Шаг не падает: выпуск и деплой от
   генерации текста не зависят. Каждый пробел источников (не получен PR, не прошла сверка пинов, нет release-notes
   компонента) выводится аннотацией `::warning` с текстом ошибки и строкой в сводке шага (`$GITHUB_STEP_SUMMARY`),
   так что зелёный прогон с дырой в фактах виден.
4. Повторный прогон на тот же тег берёт уже опубликованные `release-notes.md` и `announcement.json` как есть.
5. Бот читает `announcement.json` (`title`, `summary`, `player_changes`, `bug_fixes`, `creators`, `compatibility`,
   `color_hex`) без обработки моделью. `compatibility` показывается первым полем «⚠️ Что нужно сделать»; цвет
   задаёт CI по номеру (патч — зелёный).

`previous_version` — последний **опубликованный** релиз той же линии. Сожжённый номер, например
клиент 2.59.0 или сервер 2.60.0, в `previous_version` не ставится.

## Покрытие прошлых релизов (backfill)

Исходные assets до правок и их SHA256 лежат в рабочей папке владельца, в
`.migration/backups/release-notes-2026-09-27/`. Журнал замен — `replacements.log` там же.
Замена меняет только asset `release-notes.md`. Скрипт проверяет, что не изменились прочие assets
(digest), тег, draft/prerelease, Latest и body. Body меняется только у v2.59.1: его тело и так было

«Изменений нет» в клиентском описании допускается только при совпадении отпечатка клиентских
файлов (`client` в build.json). Отпечаток покрывает моды клиента, конфиги, ресурсы TaCZ, шейдеры,
options.txt, servers.dat, launcher.json и версии MC/Fabric. Одинаковый набор JAR этого не доказывает:
например, v2.31.15 (конфиг ModernFix), v2.38.1 и v2.39.1 (установка Java и packwiz) и v2.11.1
(тексты лаунчера и сохранение настроек) раньше ошибочно числились «без изменений».

## Инструкция автору новостей

Эти правила закреплены в промпте action (`prompts/release.md`); читайте их, если правите текст вручную.

1. Один релиз — один файл. Скачайте его:
   `gh release download <тег> -R Blockfield/blockfield-releases -p release-notes.md`.
   В лаунчере и форках файл лежит в их собственном репозитории.
2. Для новости берите «Кратко» и «Для игроков». «Обновлённые компоненты» уже содержат смысл изменений
   модов за весь промежуток версий, открывать другие релизы не нужно.
3. «В клиентской сборке изменений нет — подтверждено отпечатком» не означает, что в игре ничего
   не изменилось. Номер мог подняться ради сервера. Серверные изменения в клиентский файл не входят.
4. Пробелы источников называйте один раз, в «Источники и ограничения полноты» («Неполнота: …»). В «Для игроков»
   пункт без сведений не пишут: ни «обновлён X с vA до vB», ни «подробности не восстановлены». Отсутствие сведений
   не значит отсутствие изменений. Не додумывайте.
5. `backfilled: true` — описание восстановлено задним числом. `date` — дата исходного выпуска.
6. Про исправления безопасности пишите только, что закрыто. Не пишите, как этим пользовались.
   Не упоминайте внутреннюю инфраструктуру.
